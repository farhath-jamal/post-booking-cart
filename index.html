flowId Lifecycle

In the aggregator model, the owner of flowId is connector-vdc-v1 or connector-vdc-v3.

  • connector-vdc-v1 communicates to offermanagement-v1
  • connector-vdc-v3 communicates to offermanagement (v3)

What Is a Cart?

A cart is one offer and its offer items.

OrderRequoteRS is the cart. Offer items can be added, updated, or removed from the cart. Once added, offer items are not changed. The cart represents the state of offer items the user has selected.

Reissue Flow

ReshopOrder → RequoteOrder → UpdateOrderItems

ReshopOrder response creates an augmentation storing the flow-starting API, i.e., ReshopOrder (FLOW_INITIATION_OPERATION).

RequoteOrder / UpdateOrderItems — Routing Logic

To determine if a request is for Post Booking Ancillaries, the category of each offer item in OrderRequoteRQ is identified.

If the category cannot be found for any offer item, one of two cases applies:

  • The Post Booking Ancillaries cart has expired — for offer items already in the cart, the category cannot be found if the customer has not provided the augmentations (customers may choose not to provide augmentations after the first pricing of an offer item).
  • The Reissue cart has expired.

In both cases, an error is thrown: invalid or expired offer.

Single-Category Validation

For each OrderRequoteRQ, all offer items must belong to a single unique category. If multiple categories are detected, an error is returned requesting the customer to select only offer items of one category.

V4 can support multiple-category addition, but since V1 currently does not support this, validation is enforced. This validation can be:

  • Removed entirely if V1 adds support for all airlines.
  • Made airline-configurable if V1 adds support for select airlines only.

Cart Creation — RequoteOrder

Case 1: pricedInd = true (Pre-priced items only) — No call to V1

The full OrderRequoteRS is constructed on the V4 side. Offer items are created from augmentations and the selected offer item.

Augmentations contain:

  • segmentIds or journeyIds associated with the offer item
  • Service details: name and airline taxonomy
  • Price
  • paxIds — mapped directly from OrderRequoteRQ

Processing steps:

  1. Validate request command (offer part mainly)
  2. Process augmentations at offer item level:
    • Propagate V1 segment IDs for future OrderChange calls to V1
    • Common offer item augmentations (offerId, responseId from ServiceListRS / SeatAvailabilityRS) are carried forward, as V4 has no direct mapping for responseId
    • Standardise offer item IDs using the identifier: (paxId, segmentIds, serviceDefName) for services; (paxId, segmentId, seat) for seats
    • Validate that all offer items belong to a single category; throw an error if multiple categories detected
  3. Call OrderRetrieve to V1 (first RequoteOrder call only) — primarily to populate journeyOverview; for pre-priced items, take paxSegments, paxJourneys, originDestinations, datedMarketingSegments, datedOperatingSegments, etc. from OrderViewRS
  4. Since only pre-priced offer items are present, no call to V1
  5. Create cart:
    • Cart action = ADD for all offer items in the request
    • Add pre-priced offer items to the cart
    • Handle seat locks if seat offer items are present
    • Populate the rest of the response from OrderViewRS and OrderRequoteRQ

Case 2: pricedInd = false (Non-pre-priced items only) — Call to V1 required

Processing steps:

  1. Validate request command (offer part mainly)
  2. Process augmentations at offer item level:
    • Find V1 segment IDs for each offer item to be sent in the V1 request
    • Store the bag's requested quantity and unit price — to verify whether V1 has honoured the quantity
    • Propagate V1 segment IDs and, for non-pre-priced bag offer items, the unit price for future RequoteOrder calls
    • Common offer item augmentations (offerId, responseId) are carried forward
    • Standardise offer item IDs
    • Validate single-category rule; throw an error if multiple categories detected
  3. Call OrderRetrieve to V1 (first RequoteOrder call only) — to populate journeyOverview and standardise segment IDs and journey IDs for non-pre-priced items
  4. Call V1 with non-pre-priced offer items:
    • order_requote_rq (V4) → FlightPriceRQ (V1)
    • FlightPriceRS (V1) → order_requote_rs (V4)
    • Converted V4 response carries offer item IDs from the request; segment IDs and journey IDs are standardised
  5. Create cart — using the supplier-converted V4 OrderRequoteRS, saved with the offer expiration time limit:
    • Cart action = ADD for all offer items in the request
    • Add non-pre-priced offer items to the cart
    • Populate the rest of the response from the supplier OrderRequoteRS

Case 3: pricedInd = true and false (Mixed) — Call to V1 required

Processing steps:

  1. Validate request command (offer part mainly)
  2. Process augmentations at offer item level:
    • Find V1 segment IDs for each offer item to be sent in the V1 request
    • Store the bag's requested quantity and unit price — to verify whether V1 has honoured the quantity
    • Propagate V1 segment IDs and non-pre-priced bag unit price for future RequoteOrder calls
    • Common offer item augmentations (offerId, responseId) are carried forward
    • Standardise offer item IDs
    • Validate single-category rule; throw an error if multiple categories detected
  3. Call OrderRetrieve to V1 (first RequoteOrder call only) — to populate journeyOverview and standardise segment IDs and journey IDs for non-pre-priced items
  4. Call V1 with non-pre-priced offer items:
    • order_requote_rq (V4) → FlightPriceRQ (V1)
    • FlightPriceRS (V1) → order_requote_rs (V4)
    • Converted V4 response carries offer item IDs from the request; segment IDs and journey IDs are standardised
  5. Create cart — using the supplier-converted V4 OrderRequoteRS, saved with the offer expiration time limit:
    • Cart action = ADD for all offer items in the request
    • Add non-pre-priced offer items to the cart
    • Add pre-priced offer items to the cart
    • Handle seat locks if seat offer items are present
    • Populate the rest of the response from the supplier OrderRequoteRS

Case 4: Reissue — Always calls V3

  • order_requote_rq (V4) → order_requote_rq (V3)
  • order_requote_rq (V3) → order_requote_rs (V4)
  • Cart is created by saving the supplier-converted V4 OrderRequoteRS as-is

Cart Update Logic

When updating the cart, the following steps are performed in order:

  1. Process the cart and capture the offer item type and associated services for each offer item
  2. Identify the action for each offer item — both in the cart and in the request
  3. Execute actions in sequence:

Remove marked offer items

  • Release any occupied seats

Update marked offer items

  • Non-pre-priced offer items first:
    • Release the seat if it is a seat offer item
    • Add the seat offer item
  • Pre-priced offer items second

Retain marked offer items

  • Non-pre-priced offer items first
  • Pre-priced offer items second

Add marked offer items

  • Non-pre-priced offer items first
  • Pre-priced offer items second

Cart Clear

The cart is cleared upon successful completion of a flow-ending API. As part of this process, the existing OrderRequoteRS is removed and the cart is replaced with the orderId to indicate that the cart has been consumed.
